## Summary

This is a careful change with a real evidence base underneath it. I recomputed every measured pair in the spec's token table from the oklch values through sRGB with alpha composited and they all land within 0.05 of what is recorded, including the composited `--ring` at 50% and the destructive hue resolving to exactly the `rgb(255, 100, 103)` that `verify.md` reports. The namespace reset is genuinely load bearing: I grepped the built stylesheet across all 27 palette families and all 15 colour prefixes the guard knows about and found nothing. `src/main.test.ts` is a real behavioural test — I removed `<MotionConfig reducedMotion="user">` and it goes red on the transform assertion, and read `motion-dom`'s source to confirm why.

The headline problem is that the guard, which the spec calls "load bearing rather than redundant", has a hole straight through the class-attribute path it exists to police, and a second hole in the token layer's own existence check. Both are demonstrable end to end: the suite stays green and the build emits a hardcoded hue. Beyond that, two of the five new primitives ship with defects that no test can see because no test looks at their behaviour, and the popup's row entrance runs on motion's default springs, which bounce, in the same component where the author converted the progress tween to a duration citing the rule against exactly that.

## Major

### 🟠 The guard misses a named CSS colour inside an arbitrary value, `src/testing/guards/design-tokens.ts:116`

**Problem**: `COLOUR_LITERAL` matches hex literals and colour *functions*. It does not match a bare CSS colour keyword, so `bg-[red]` is not an `arbitrary-colour` violation. The guard is blind to the whole family:

```
bg-[red]                                   GUARD MISSES   →  background-color:red
text-[tomato]                              GUARD MISSES   →  color:tomato
bg-[color:red]                             GUARD MISSES   →  background-color:red
shadow-[inset_0_0_0_1px_red]               GUARD MISSES   →  box-shadow: … red
border-[3px_solid_red]                     GUARD MISSES   →  border-color:red
ring-[2px_red]                             GUARD MISSES   →  --tw-ring-color:red
fill-[crimson]                             GUARD MISSES
```

I confirmed this is not theoretical. With `text-[crimson]` on `src/App.tsx:277`:

- `npx vitest run` → **205 passed**, including `guards.test.ts`'s "finds no raw colour in the real source tree"
- `npx vite build` → the shipped stylesheet contains `.text-\[crimson\]{color:#dc143c}`

and it is the only chromatic declaration in the entire built CSS, which is the closest thing to a controlled experiment this finding needs.

**Why it matters**: This is squarely inside the match set AC-2 claims. `index.md:211-212` says the guard fails on "any arbitrary value containing a colour, so `shadow-[0_0_15px_rgba(168,85,247,0.2)]` and `bg-[#7c3aed]` both fail" — the second example is a hex and the first a function, and the author implemented exactly those two shapes. A keyword is the third shape, it is the shortest one to type, and it is the one the guard does not catch. `index.md:488-489` states the failure mode this standard exists to prevent: "A raw colour utility builds fine and then does nothing". Here it is worse — it builds fine and then *does something wrong and vivid*, with a green test suite certifying the design language holds.

**Suggested fix**: Add a keyword set to `design-tokens.ts` covering the CSS named colours plus the system keywords Tailwind's arbitrary-value path accepts (`transparent`/`currentColor` stay exempt under the existing rule), and test `bg-[red]` and `text-[tomato]` in the fixture set alongside the two existing arbitrary-value cases. Worth deciding explicitly whether `oklab`/`lab`/`lch` without arguments and `color(display-p3 …)` are in scope too, so the boundary is written down rather than discovered later.

### 🟠 The token this change introduced is the one token nothing checks, `src/design-language.test.ts:18`

**Problem**: `colourReferences()` walks `uiDir = join(srcDir, "components", "ui")` and nothing else. `--subtle-foreground` is a **new** token added by this change, and it is referenced only from `src/App.tsx` — 11 times, from the section headings and metadata lines through to the version chip. No primitive under `components/ui/` uses it, so the AC-4 test never sees it.

I deleted `--subtle-foreground: oklch(0.65 0 0);` from `:root` in a clean copy of the tree:

- `npx vitest run` → **205 passed**. Every other token I tried (`--card`, `--input`, `--destructive`) turns AC-4 red, because a primitive references it. This one does not.
- `npx vite build` → the stylesheet still emits `.text-subtle-foreground{color:var(--subtle-foreground)}` and `--subtle-foreground` is defined nowhere.

The rule survives; the value does not. Every one of those 11 text nodes then resolves to an invalid colour and inherits.

**Why it matters**: This is the exact class of failure the namespace reset makes silent and the guard exists to make loud, landing on the one token whose whole purpose is new in this change. The prior review flagged that the AC-4 scan is scoped one directory short of the two compositions; the sharper form of that is that scoping it to `components/ui` is not the problem, scoping it to *source files at all* is — the compositions would be caught by a scan pointed at `src/components`, but `App.tsx` would not be caught by either. Deleting a token from the token layer and shipping a popup with no metadata colour anywhere, suite green, is a one-line mistake that nothing in this change's 205 tests objects to.

**Suggested fix**: Widen `primitiveSources()` to walk all of `src`, or add a second pass that resolves every `bg-*`/`text-*`/`border-*`/etc. token reference in the non-primitive source against `definedTokens()`. The fixture at `design-language.test.ts:117-120` already has the shape for it: assert the scan found references, then assert they all resolve. Add one case per new token so a future token cannot be added without landing inside the check.

### 🟠 `progress` emits invalid CSS above 100 and renders a full bar, `src/components/ui/progress.tsx:27`

**Problem**: `style={{ transform: \`translateX(-${100 - (value || 0)}%)\` }}` has no clamp. I rendered the component and read the markup:

| `value` | rendered indicator |
|---|---|
| `0` | `transform:translateX(-100%)` |
| `40` | `transform:translateX(-60%)` |
| `100` | `transform:translateX(-0%)` |
| `140` | `transform:translateX(--40%)` |
| `undefined` | `data-state="indeterminate"`, `translateX(-100%)` |

At `140` the declaration is not a valid transform, the CSS parser drops it, and the indicator falls back to its own `size-full flex-1` — a bar reading 100% complete. `bytesReceived > totalBytes` is reachable: `totalBytes` is the declared size and `bytesReceived` counts the whole received body, so a redirect or a resumed transfer produces exactly that. The spec asks for the opposite, "otherwise `Math.round(bytesReceived / totalBytes * 100)` **clamped to 100**" (`index.md:369`).

In the indeterminate case, which the spec names as the real one ("`totalBytes <= 0` being the only indeterminate case", `index.md:339`), the indicator is parked 100% off a track it shares the full width of, and there is no `data-[state=indeterminate]:` rule anywhere in the class list. So an in-flight download of unknown length renders a static grey line, indistinguishable from a stalled transfer.

**Why it matters**: Both branches lie about the state of a transfer, which is the one thing this design language exists to prevent, and neither is covered: `progress.test.ts` renders `value: 40` three times and asserts three class names, so the suite is green with the component wrong in both directions.

**Suggested fix**: Clamp into 0..100 before it reaches the style, give the indeterminate case a stated treatment (a `data-[state=indeterminate]:` sweep gated on `motion-safe:`, or an explicit spec decision that empty-bar-plus-text is the answer), and add both cases to `progress.test.ts`. They fail today.

### 🟠 The row entrance and exit run on springs that overshoot, `src/App.tsx:300`

**Problem**: `StreamCard`'s `motion.div` declares `initial={{ opacity: 0, y: 8 }}` / `animate={{ opacity: 1, y: 0 }}` with `transition={{ delay: idx * 0.03 }}` and no duration or type; `exit={{ opacity: 0, scale: 0.95 }}` at line 303 is the same. I read the motion source to confirm the mechanism rather than assume it: `is-transition-defined.mjs` treats `delay` as an orchestration key and returns `false`, so `getDefaultTransition` applies. That function routes `y` to `underDampedSpring { stiffness: 500, damping: 25 }` and `scale` to `criticallyDampedSpring(0.95) { stiffness: 550, damping: 30 }`. Neither name is accurate: both damping ratios are `c / (2√k)` = 0.559 and 0.640, comfortably under 1. Every row overshoots its final position and settles back. `opacity` gets the 0.3s keyframes ease, over the spec's 200ms ceiling. The YouTube banner at `src/App.tsx:173-177` has the same shape with `y: -10`.

The spec is explicit: "Entrances ease out, exits ease in. **No bounce, no overshoot, no spring on a list.**" and "nothing over 200ms" (`index.md:432-434`). The author applied that rule 76 lines below, converting the progress tween from `{ type: "spring", bounce: 0, duration: 0.3 }` to `{ duration: 0.15, ease: "easeOut" }` at `src/App.tsx:380`, and left the springs on the list, where the rule is most pointed.

**Why it matters**: This is the animation a person sees every time they open the popup, and it bounces. It is invisible in jsdom, which is why `/check verify` did not catch it.

**Suggested fix**: An explicit tween on both `motion.div`s, matching the one already on the progress bar: `easeOut` around 0.15s for entrance, `easeIn` for exit. Two lines, and inside this feature since AC-8 and the motion rules are its own criteria.

## Minor

### 🟡 The version chip is 0.01 of contrast above the floor the spec calls the floor, `src/App.tsx:281`

**Problem**: `<span className="text-[9px] font-bold text-subtle-foreground">v1.1.0</span>` sits on `<div className="... bg-muted ...">`. Composited: `--subtle-foreground` on `--muted` is **4.51:1**. That is the lowest enabled text node in the popup — I checked every rendered pair, and the next lowest is `--muted-foreground` on `--muted` at 5.88:1.

The spec's token table measures `--subtle-foreground` only against background (6.12:1) and card (5.33:1) and then declares it the floor: "the faintest grey that still clears 4.5:1 on card is L=0.61, so `--subtle-foreground` at `0.65` is the floor for any enabled text" (`index.md:260-262`). Nothing in the table covers `--muted` as a backdrop, and the accessibility rules say that exemption "never applies to enabled content" (`index.md:415-416`).

**Why it matters**: 4.51:1 clears AA by one hundredth. Any darkening of `--muted` puts this element below the bar, and the spec has no recorded measurement that would catch it — the token table would still read 5.33:1 for card and the author would have no reason to re-check. The version string is also the least informative text in the popup, so it is the cheapest thing to move.

**Suggested fix**: Either put the chip on `--muted-foreground` (5.88:1 on the same surface, no new token) or add the `--muted` backdrop as a measured row in the spec's text table so the surface is on the record. Worth doing either way, since `--muted` is now used as a backdrop for icons, chips and the progress track and the table has no row for it.

### 🟡 `transition-colors` cannot animate the hover ring it was added for, `src/App.tsx:306`

**Problem**: The row's class string is `transition-colors group overflow-hidden shadow-none hover:ring-ring/50`. The hover state changes the ring's colour, which Tailwind writes to the `--tw-ring-color` custom property. I read the built `.transition-colors` rule: `transition-property:color,background-color,border-color,outline-color,text-decoration-color,fill,stroke,--tw-gradient-from,--tw-gradient-via,--tw-gradient-to`. `--tw-ring-color` is not in it, and it is not in the hover rule's own declaration either. So the ring snaps from 1.31:1 to 3.60:1 instantly while the class on the element promises a transition.

**Why it matters**: Small, but it is the class the migration added specifically to carry the hover affordance, so it does not do the one thing a `transition-*` class is for. `transition-all` would cover it and is what the row had before.

**Suggested fix**: Either `transition-all`, or name the properties (`transition-[--tw-ring-color]`), or move the hover affordance onto `border-color` so the existing `transition-colors` covers it. Worth a sentence in the spec's Motion rules, since "state change on an existing element is 100ms" (`index.md:431`) is a rule nothing currently tests.

### 🟡 The popup's own progress bar has no clamp and no accessible value, `src/App.tsx:370`

**Problem**: `width: downloadState.totalBytes > 0 ? \`${(bytesReceived / totalBytes) * 100}%\` : '30%'`. No clamp, so the same `bytesReceived > totalBytes` case that breaks the primitive renders a `width` over 100% here, clipped by the Card's `overflow-hidden` rather than by a decision. The track `div` carries no `role` and no `aria-valuenow`, so the value is visual only.

This is the `30%` the spec's Replaces list names as deleted ("the `30%` placeholder and `duration: 0.3` spring", `index.md:181`): the spring is gone, the placeholder is not, and `scope.md` records the migration as complete. The Components table states the guarantee the new primitive exists to provide — "determinate from real bytes, `totalBytes <= 0` being the only indeterminate case, **never a faked 30%**" (`index.md:339`) — and the popup is the one place that fakes it. The spec also asks that the percentage be "both the visible label and the progress element's accessible value, so the number a person reads and the number a screen reader hears cannot disagree" (`index.md:369`); today a screen reader hears nothing at all.

**Why it matters**: Pre-existing and mostly harmless, but it is the one item on a Replaces list that was marked done without being done, and it is a progress indicator reporting a number that is not true.

**Suggested fix**: Clamp alongside the primitive, and either move this onto build plan task 6 explicitly so slice 1 inherits it as a named item, or delete the `'30%'` branch and let `totalBytes <= 0` render an empty track until the first real measurement arrives. The accessible value is task 6's job and is named there, so no action needed on that half now.

### 🟡 The spec justifies keeping `--input` with references that can never fire, `docs/specs/0003-popup-design-language/index.md:146`

**Problem**: The paragraph explains why `--input` survives the deletion of `--popover`/`--sidebar*`/`--chart-*`: "because the generated primitives reference them today: … `border-input`, `bg-input/30`, `bg-input/50` … Dropping them would silently unstyle the secondary button variant, the outline button's border and every card footer hover." I grepped every reference to `input` in `src/components/ui/`. There is exactly one, and all three utilities in it are `dark:`-prefixed: `src/components/ui/button.tsx:14`, `dark:border-input dark:bg-input/30 dark:hover:bg-input/50`.

The same document's Consequences section states the reason those cannot fire: "Dark is unconditional, so `dark:` variant utilities never fire" (`index.md:500-501`). I confirmed nothing anywhere sets a `.dark` class — no `classList.add`, no `class="dark"` in `index.html`. The card footer hover claim is also wrong on its own terms: `card.tsx:87` uses `bg-muted/50`, not anything `input`-shaped.

**Why it matters**: The stated reason for keeping a token is false, in a section AC-4 leans on. Today the token is protected by accident, because AC-4 sees the class reference whether or not the `dark:` variant can fire — delete `--input` and the test goes red. But a future reader who correctly concludes the `dark:` references are dead, deletes those utilities as dead code, and then deletes the token as newly-unused is following this document's own logic. The document contradicts itself in the same file, thirty lines apart.

**Suggested fix**: Either drop the `dark:` utilities from the generated primitives as part of this change, so the justification becomes true and the palette shrinks, or correct the paragraph to say `--input` is retained only because a generated primitive references it, and note that the reference is inside a `dark:` variant that cannot fire. The first is cleaner and matches the spec's own "Neutral" note; the second is honest and cheap.

## Strengths

- **The contrast work is real and the numbers hold up.** I recomputed all fourteen measured pairs from the oklch values through sRGB with alpha composited in device space, and every one lands within 0.05 of the spec, including the composited `--ring` at 50% (3.15:1 measured against a stated 3.14:1), the 10%-white border the spec rejects (1.34:1 against a stated 1.32:1), and the destructive hue resolving to exactly `rgb(255, 100, 103)` — the value `verify.md:85` reports. That is a better evidence base than most design specs have, and it is what made the rest of this review cheap.
- **The namespace reset is genuinely load bearing.** I grepped the built stylesheet across all 27 palette families and all 15 colour prefixes the guard knows about, plus a separate scan for any chromatic declaration in the whole file: zero, apart from the one this review's own experiment injected. `--color-*: initial` placed after the imports does what the spec says it does.
- **`src/main.test.ts` is the best test in the change.** It mounts the real entry, stubs `matchMedia` and the extension API, and asserts on what motion writes to the DOM. I removed `<MotionConfig reducedMotion="user">` and it goes red on the transform assertion. I also confirmed the mechanism in `motion-dom`'s source rather than trusting the test: `initPrefersReducedMotion` reads exactly `(prefers-reduced-motion)`, which is what the stub matches, so the test is exercising the real code path and not a coincidence.
- **The guard's parsing is more careful than it needed to be, and the care is tested.** The nested-bracket walk in `arbitraryGroups` and the deliberate lookbehind allowance for `_` in `COLOUR_LITERAL` are both cases most implementations get wrong, and each has a fixture that fails if the reasoning regresses. The self-test that reads `node_modules/tailwindcss/theme.css` and fails when the palette list drifts is exactly the thing that stops a hole opening in a later Tailwind release — which makes the two holes this review found more interesting, not less: the author built the right scaffolding and then did not fill in one column of it.
- **The `Unknown_Page` fix at `src/App.tsx:97-105` is a real bug found and fixed properly.** The comment explains why the guard sits after sanitising rather than before, which is the non-obvious half, and four table-driven cases cover empty, whitespace-only and punctuation-only titles. It is also the only behavioural bug fix in the change, and it came with a test that fails if the fix is reverted.
- **Two guard-design decisions that authors usually get wrong in the direction of false confidence, both got right.** `collectSourceFiles` takes the extension list as an additive parameter instead of widening the default, so the purity guard is unaffected; and `collectDesignTokenViolations` throws on a missing source tree rather than reporting a clean run, because it cannot tell "no violations" from "no tree". The comment says exactly that, and there is a test for it.
- **`AC-3`'s white-canvas bug was found and fixed rather than assumed away.** The old `hsl(var(--background))` against an `oklch` value was invalid, so the property fell back to transparent and the popup sat on the white canvas. The suite is strong on what is easy to assert and honest about what is not.
