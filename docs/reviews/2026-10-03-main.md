## Summary

This is the walking skeleton slice: a pure `src/engine/` holding the rules, a service worker reduced to an `onHeadersReceived` observer plus a five message router, a content script cut down to reporting the page title and URL, a popup rebuilt on the design language, and the harness fakes to prove all of it with no browser. The architecture is genuinely well executed: the purity boundary is enforced by a guard rather than a convention, the message contract is parsed on both ends, identity and the hidden count are derived rather than accumulated, and every one of the five defects that three runtime verification passes found now has a test that fails on the old code. The problems below are all in the error handling around messages and in one comment that states a platform behaviour the runtime contradicts.

## Major

### 🟠 Five fire and forget promises in the worker, none of them caught, `src/background.ts:270`

**Problem**: every call site that starts asynchronous work discards the promise. `void recordFinding(...)` at line 270, `void queue.run(...)` at line 348, and `void applyEntriesReport(...).then(sendResponse)` at 589, `void readTabMedia(...).then(sendResponse)` at 594, `void startDownload(...).then(sendResponse)` at 599. `createSerialQueue` deliberately keeps its stored chain from rejecting (`src/engine/merge.ts:257`), so a rejecting task produces an unhandled rejection in the worker rather than poisoning the queue, which is the right design for the queue and the wrong design for the callers. The router's `.then(sendResponse)` is the worse half: if the handler rejects, `sendResponse` is never called, so the response channel stays open and the popup's `await chrome.runtime.sendMessage` never settles.

**Why it matters**: the realistic triggers are ordinary, not exotic. `chrome.action.setBadgeText` for a tab that closed between the observer firing and the badge write rejects, and `chrome.tabs.onRemoved` races exactly that. A worker terminated while handling a message rejects the sender. Each of those produces an unhandled rejection that Chrome logs on every occurrence, and in the router's case a popup that waits forever for an answer that will never come. That last shape is the same user visible symptom as the defect `/debug` just fixed, which is why it is worth closing now rather than after the next report.

**Suggested fix**: catch at the boundary rather than at each site. In the router, `void handler(...).then(sendResponse, (error) => { droppedMessages += 1; sendResponse(undefined) })`, so a rejection still answers the channel and the popup's promise settles. At the three `void` sites, attach a `catch` that counts the failure, since `droppedMessages` and the diagnostics view (scope feature 16) already exist for exactly this. Then add the tests, because none of this is covered and the guide treats untested error handling as a finding in its own right.

### 🟠 The popup awaits two messages with no catch, so a rejection strands the row, `src/App.tsx:113` and `src/App.tsx:198`

**Problem**: `readOnce` awaits `chrome.runtime.sendMessage` bare, and `download` does the same. `read`'s `try/finally` clears `readingRef`, so the next trigger recovers, but the rejection itself escapes: the mount effect's `void Promise.resolve().then(read)` becomes an unhandled rejection, and nothing tells the person anything. `/test` recorded this as its one deliberate coverage gap rather than writing a test around undefined behaviour, which was the right call then and is the reason it is a finding now.

**Why it matters**: the popup's read is the only thing that can put a content script on a page, and its failure modes are the ones a person cannot act on. A read that rejects leaves the watching state with no hint and no explanation, which is the dead end `/check verify` found in a different form.

**Suggested fix**: decide what the popup shows when a read fails, then make the two call sites say it. A read failure is most honestly `status: 'unsupported'` with the existing named notice, since that is what "I could not reach the worker" means to a person. A download failure already has a copy string waiting, so catching and using it is a two line change.

### 🟠 The file header states a platform limitation the runtime contradicts, `src/background.ts:11`

**Problem**: the header says the top level registration is "also the chosen limitation in AC-18: media requested while the worker was gone is not seen." `/check verify` measured that on 2026-10-02 and it is not what happens: with the worker's target closed and the worker count at zero, a media request brought it back within 120 ms and the file was in the record. A `chrome.webRequest` registration survives the worker being stopped and Chrome starts the worker for a matching event, so the registration is not the limitation and detection continues across a stop.

**Why it matters**: this is the first thing a reader of the service worker sees, and it is the stated reason for a design decision. Someone reading it will add retry logic, a queue, or a worker lifetime workaround for a problem that does not exist, and will not think to test the case where a request arrives while the worker is down because the comment says it cannot be recorded.

**Suggested fix**: correct the comment to what was measured, and say what the real limitation is, which is that media which finished before anything was listening is not seen retrospectively. Spec 0004's AC-18 needs the same correction, which is `/architect`'s to make; the comment is this change's to fix. `/check verify` wrote both findings up in the feature's `verify.md`.

## Minor

### 🟡 The observer writes and broadcasts on every response, including ones that change nothing, `src/background.ts:230`

**Problem**: `recordFinding` merges, saves, sets the badge and broadcasts unconditionally. `mergeDrafts` returns a `TabMedia` and no indication of whether anything moved, so the observer cannot skip a no-op the way its sibling does: `applyEntriesReport` saves only `if (applied.changed)` and says why in a comment (line 553). A page that re-requests a file it is already playing therefore costs a storage write, a badge write and a broadcast per request.

**Why it matters**: harmless at one request, wasteful on a page that polls its own media, and it makes the two paths inconsistent for the next reader. An open popup re-reads on each broadcast, so the cost lands there too.

**Suggested fix**: have `mergeDrafts` report whether it changed anything, the way `applyReport` already does, and skip the save, the badge and the broadcast when it did not. That keeps the storage quota for real findings.

### 🟡 The worker's specific download errors can never reach anyone, `src/App.tsx:205`

**Problem**: `startDownload` returns three distinct messages ("There is no tab to download from", "That file is no longer listed for this page", "That file cannot be saved on its own") and the popup discards `response.error`, writing the fixed string "Download failed" instead.

**Why it matters**: the strings are unreachable, and the row tells a person nothing they can act on when the real answer is "that file is not a single file". The popup is spec compliant here, because AC-17 fixes that copy, so the finding is about dead text rather than wrong behaviour, and about the diagnostics view that scope feature 16 will want.

**Suggested fix**: either surface `response.error` when it is present and keep "Download failed" as the fallback (which needs an AC-17 amendment, so `/architect` first), or delete the three strings and leave one comment saying why the copy is fixed.

### 🟡 The page claim is stamped with the contract version, which does not move during development, `src/content.ts:58`

**Problem**: `claimPage()` compares `STAMP_KEY` against `CONTRACT_VERSION`. After an extension reload the stamp still matches, so a re-injected script returns early and the previous build's content script keeps running and keeps reporting.

**Why it matters**: in the development loop this reads as "my content script changes do nothing", and the cost is a confusing afternoon rather than a production bug. The comment already explains the intent, so the gap is only in the stamp's discriminating power.

**Suggested fix**: stamp something that changes per build, such as the extension's own `runtime.id`, alongside the contract version. The mismatch case the comment describes stays exactly as it is.

### 🟡 Whole subtree observation on every page the popup is opened on, `src/content.ts:83`

**Problem**: `observer.observe(document.body, { childList: true, subtree: true })` fires the callback for every DOM insertion anywhere in the page. The callback is trivial, but the volume is not: a feed or a video page mutates constantly. Two smaller edges come with it. `history.pushState` fires no DOM event, so a route change with no accompanying mutation is missed until the next mutation of any kind. And `if (document.body)` means a script injected before the body exists silently never attaches, with no signal that URL tracking is off.

**Why it matters**: this runs on arbitrary pages by design, since injection is on demand. It is the one place in the slice whose cost scales with someone else's page.

**Suggested fix**: hook `history.pushState`, `replaceState` and `popstate` for URL changes, which is both cheaper and more reliable than watching the DOM, and keep the observer only if something else needs it. Make the missing body case explicit rather than silent.

### 🟡 The filename rule rejects illegal characters but not Windows reserved names, `src/engine/filename.ts:12`

**Problem**: `REJECTED` covers `/ \ : * ? " < > |` and control characters are stripped, but `CON`, `PRN`, `AUX`, `NUL`, `COM1` to `COM9` and `LPT1` to `LPT9` pass through. A page whose title is `CON` produces `CON.mp4`, which Windows will not create.

**Why it matters**: the page title is arbitrary text from an untrusted page, and this rule exists to turn exactly that into a safe file name. I have not confirmed whether Chrome's downloads API sanitises reserved names itself, so this may be handled downstream; that is worth checking rather than assuming.

**Suggested fix**: one line rejecting those stems after sanitising, with a test for `CON` and `LPT1`. If Chrome already handles it, say so in a comment instead, so the next reader does not re-derive it.

## Nits

- ⚪ `src/content.ts:83`, the URL tracking comment says a timer "would keep running on every tab for as long as it is open", which is true of a polling timer but reads oddly next to a `MutationObserver` that also runs for as long as the page is open. Worth a sentence on why the observer was chosen over the timer it dismisses.
- ⚪ `src/background.ts:63`, blocking every `*.chrome.google.com` host is broader than the store listing pages the comment names, and will grow to block unrelated Google properties over time. An exact host list plus the paths that matter would age better.
- ⚪ `src/App.css` and `src/assets/` (four files, including `react.svg` and `vite.svg`) are referenced by nothing in the project. Pre existing rather than part of this change, but this is the slice that rewrote both entry points, so it is the natural moment to notice them.

## Strengths

- The engine boundary is enforced rather than agreed. `src/testing/guards/engine-purity.ts` fails the build when a module under `src/engine/` reaches a browser API, and the co located test guard fails when one has no test. That is what makes 178 engine tests runnable with no `chrome` global defined at all, and it is the single best decision in the change.
- The hidden count is derived from the distinct identities seen less what is held, so an entry dropped at the cap and seen again is not counted twice. Accumulating it was the obvious implementation and would have been quietly wrong.
- The per tab serial queue stores a chain that cannot reject, with a comment saying exactly why. That is the kind of detail that is normally got wrong and then blamed on Chrome.
- Each of the five defects found by runtime verification has a regression test that fails on the old code, and two of the three popup tests were checked by breaking the fix two ways and confirming the same tests fail. Tests that cannot fail are worse than no tests, and these were shown to bite.
- The fakes are narrow by construction: `types.ts` owns the surface the extension actually calls, so a fake cannot grow a method nothing uses.

## Test coverage

534 tests across 28 files, with the engine fully covered and no browser present. The gaps that matter are all one family: every rejection path in the worker and the popup is untested, which is why both Majors above are also coverage findings. Specifically uncovered: a handler that rejects while holding a response channel, `chrome.action.setBadgeText` for a tab that has just closed, a read or download message that rejects, and `GET_TAB_MEDIA` naming a tab other than the sender's. The `file:` unhostable case is untestable in the environment this ran in, since that Chromium grants an unpacked extension access to file urls; that is an environment limit rather than a suite gap, and it is why the dead end described in the second Major is reasoned from the code rather than measured.
